MyVector distance kernels on AMD EPYC · Intel Xeon · ARM Neoverse — measured on real silicon · generated 2026-11-07 00:03:59 UTC

← cross-engine (fashion-mnist) · real-dataset · glove · village

PR #278 (merged to main, commit 1cf3030) vectorized MyVector's three scalar HNSW distance kernels — L2Sqr, InnerProduct, and computeCosineDistance — which previously ran scalar in every shipped build on every CPU. This page validates that the speedup is not arm-specific: it reproduces on AMD and Intel x86 silicon, and the optimized component runs end-to-end on a real x86 host. Numbers are measured on GitHub-hosted runners (the project's OCI tenancy cannot launch an x86 host — Free-Tier account block); read the honest caveats below before comparing absolute throughput across chips.

1 · Kernel speedup (scalar → vectorized), same-runner A/B

A self-contained microbench of the exact kernel loops, compiled at each optimization level and run back-to-back within one job on one runner (so the ratio is a valid A/B). Figures are L2Sqr at 784-d (the fashion-mnist dimensionality), in millions of distances/sec. SSE is what the portable default build emits from the PR #278 reassoc-math pragma; AVX2/AVX-512 need -march.

Reading it: the win holds on every ISA. SSE ≈ AVX2 on both x86 vendors and AVX-512 adds only ~14% — the high-dim kernel is memory-bandwidth-bound, so wider lanes don't help. That means the portable SSE build (no -march) already captures the full win — a correctness/portability win, not a compromise. (Absolute Mdist/s differ by chip mostly because the GHA AMD runners have ~1.8× the per-core memory bandwidth of the Intel ones; the speedup ratio is the comparable quantity.)

Caveats & honesty

  • Why GitHub runners: the project's OCI tenancy is a post-trial Free-Tier account and cannot launch any new instance (x86 or ARM) until a console-side Pay-As-You-Go upgrade. GHA x86 runners were the available real-x86 silicon. A persistent OCI x86/Intel host (for larger/longer end-to-end runs) remains the one piece pending that upgrade.
  • What is and isn't an A/B: the §1 kernel table is a valid A/B (variants run back-to-back on one runner). An end-to-end cross-dispatch A/B on GHA is not valid — separate dispatches land on different, differently-loaded machines; an attempt hit different CPUs (9V45 vs 9V74) and was discarded as confounded (identical recall confirmed it was noise, not a code change). The end-to-end PR #278 gain is instead shown by a same-host A/B on the ARM dev box (+9% at ef=20 → +37% at ef=800, monotonic with ef — the kernel-speedup signature), consistent with the kernel being a larger share of the query at higher ef.
  • Synthetic data: §2 uses synthetic vectors (fast, deterministic) with recall vs exact brute-force. The engine-vs-engine pages (glove, real, village) use real ann-benchmarks datasets with published ground truth.
  • Shared runners: absolute end-to-end QPS from a shared 4-core runner is indicative, not a tuned-host number; treat §2 as "the optimized build runs correctly and at reasonable throughput on x86," not as a peak-performance claim.
